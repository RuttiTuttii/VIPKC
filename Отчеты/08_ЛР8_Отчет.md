### 3.1 Подготовка ресурсов и переменных окружения (Пункты 1 и 2)

Для включения ускоренной параллельной сборки и кэширования слоев активирован движок BuildKit. Для исключения запуска контейнеров от пользователя root и предотвращения блокировки файлов на хосте написан скрипт `00_env_setup/setup_env.sh`, передающий в контейнеры реальные `$UID` и `$GID` пользователя хоста.

#### Листинг скрипта настройки окружения (`00_env_setup/setup_env.sh`):

```bash
#!/usr/bin/env bash
# скрипт настройки системных переменных docker и пользовательского окружения
set -euo pipefail

# активация buildkit для ускоренной сборки
export DOCKER_BUILDKIT=1
export COMPOSE_DOCKER_CLI_BUILD=1
export COMPOSE_PROJECT_NAME="vipkc_lab8"

# пользовательские переменные для не-root запуска сервисов
export APP_USER="${USER:-eegor}"
export APP_UID="$(id -u)"
export APP_GID="$(id -g)"
export APP_TIMEZONE="Europe/Moscow"

cat <<EOF > "$(dirname "$0")/.env"
USER=${APP_USER}
UID=${APP_UID}
GID=${APP_GID}
TIMEZONE=${APP_TIMEZONE}
COMPOSE_PROJECT_NAME=${COMPOSE_PROJECT_NAME}
EOF

echo "окружение настроено: UID=${APP_UID}, GID=${APP_GID}, BUILDKIT=1"
```

### 3.2 Управление проектом игры 2048 через собственный образ реестра (Пункт 3)

Исходный код игры 2048 взят из собственного GitHub-репозитория `RuttiTuttii/2048`. Для максимальной оптимизации и безопасности сформирован минимальный образ на базе `nginx:1.27.4-alpine3.21-slim` с конфигурацией безопасности и проверкой жизнеспособности `/healthz`.

#### Листинг `01_game_2048/Dockerfile`:

```dockerfile
# минимальный базовый образ lts на alpine
FROM nginx:1.27.4-alpine3.21-slim

LABEL maintainer="Egor Radin <glutinosa@users.noreply.github.com>"
LABEL org.opencontainers.image.version="1.0.0"

# удаляем дефолтные файлы nginx и подключаем свой виртуальный хост
RUN rm -rf /usr/share/nginx/html/* /etc/nginx/conf.d/default.conf
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY src/ /usr/share/nginx/html/

# права только на чтение статики
RUN chmod -R 755 /usr/share/nginx/html

# встроенный healthcheck
HEALTHCHECK --interval=15s --timeout=3s --start-period=5s --retries=3 \
    CMD wget -q --spider http://127.0.0.1:80/healthz || exit 1

EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

#### Листинг `01_game_2048/docker-compose.yml`:

```yaml
services:
  game-2048:

    restart: unless-stopped
    build:
      context: .
      dockerfile: Dockerfile
    ports:
      - "${GAME_PORT:-4448}:80"
    environment:
      - TZ=${TIMEZONE:-Europe/Moscow}

      resources:

          cpus: "0.50"

      retries: 3
      start_period: 5s
    logging:
      driver: "json-file"
      options:
        max-size: "10m"
        max-file: "3"
    networks:
      - game_net

networks:
  game_net:
    name: vipkc_game_net
    driver: bridge
    ipam:
      driver: default

        - subnet: 172.28.10.0/24
```

### 3.3 Развертывание хостинга репозиториев Gitea с СУБД MySQL (Пункт 4)

Спроектирована отказоустойчивая двухзвенная архитектура:
1. База данных `mysql:8.4.4` помещена в изолированную внутреннюю сеть `gitea_backend` с параметром `internal: true`. Внешний трафик в эту сеть заблокирован, порт 3306 на хост не публикуется.
2. Сервис `gitea/gitea:1.22.6` подключен одновременно к внешней сети `gitea_frontend` (порты 4430 для web и 4422 для SSH) и к внутренней сети `gitea_backend`.
3. Запуск Gitea отложен до успешного завершения `healthcheck` СУБД MySQL через директиву `depends_on: condition: service_healthy`.

#### Листинг `02_gitea_mysql/docker-compose.yml`:

```yaml
services:
  gitea-db:
    image: mysql:8.4.4
    container_name: vipkc_gitea_mysql
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD:-mysql_super_root_password_2026}
      MYSQL_DATABASE: ${MYSQL_DATABASE:-gitea}
      MYSQL_USER: ${MYSQL_USER:-gitea_user}
      MYSQL_PASSWORD: ${MYSQL_PASSWORD:-gitea_secure_password_2026}
      TZ: ${TIMEZONE:-Europe/Moscow}
    volumes:
      - gitea_mysql_data:/var/lib/mysql
    # база данных изолирована во внутренней сети
    networks:
      - gitea_backend
    healthcheck:
      test: ["CMD-SHELL", "mysqladmin ping -h 127.0.0.1 -u $$MYSQL_USER -p$$MYSQL_PASSWORD || exit 1"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s
    deploy:
      resources:
        limits:
          cpus: "1.00"
          memory: 512M

  gitea-app:
    image: gitea/gitea:1.22.6
    container_name: vipkc_gitea_server
    restart: unless-stopped
    depends_on:
      gitea-db:
        condition: service_healthy
    environment:
      - USER_UID=${USER_UID:-1000}
      - USER_GID=${USER_GID:-1000}
      - GITEA__database__DB_TYPE=mysql
      - GITEA__database__HOST=gitea-db:3306
      - GITEA__database__NAME=${MYSQL_DATABASE:-gitea}
      - GITEA__database__USER=${MYSQL_USER:-gitea_user}
      - GITEA__database__PASSWD=${MYSQL_PASSWORD:-gitea_secure_password_2026}
      - GITEA__server__DOMAIN=localhost
      - GITEA__server__SSH_PORT=${GITEA_SSH_PORT:-4422}
      - GITEA__server__ROOT_URL=http://localhost:${GITEA_HTTP_PORT:-4430}/
      - TZ=${TIMEZONE:-Europe/Moscow}
    volumes:
      - gitea_app_data:/data
      - /etc/timezone:/etc/timezone:ro
      - /etc/localtime:/etc/localtime:ro
    ports:
      - "${GITEA_HTTP_PORT:-4430}:3000"
      - "${GITEA_SSH_PORT:-4422}:22"
    networks:
      - gitea_frontend
      - gitea_backend
    healthcheck:
      test: ["CMD-SHELL", "curl -f http://127.0.0.1:3000/api/v1/version || exit 1"]
      interval: 15s
      timeout: 5s
      retries: 3
      start_period: 20s

networks:
  gitea_frontend:
    name: vipkc_gitea_frontend
    driver: bridge
    ipam:
      driver: default
      config:
        - subnet: 172.28.20.0/24
  gitea_backend:
    name: vipkc_gitea_backend
    driver: bridge
    internal: true
    ipam:
      driver: default
      config:
        - subnet: 172.28.21.0/24

volumes:
  gitea_mysql_data:
    name: vipkc_gitea_mysql_data
  gitea_app_data:
    name: vipkc_gitea_app_data
```

### 3.5 Управление файловым хостингом FileBrowser на порту 4444 (Пункт 6)

Развернут легковесный файловый менеджер `filebrowser/filebrowser:v2.63.23`.  
* **Уникальный порт:** Выделен внешний порт `4444:80`.
* **Безопасность прав:** Директива `user: "${UID:-1000}:${GID:-1000}"` запускает процесс под обычным пользователем хоста, благодаря чему загружаемые файлы в директории `srv/` не блокируются root-правами.

```yaml
services:

    restart: unless-stopped

    user: "${UID:-1000}:${GID:-1000}"
    ports:
      - "${FILEBROWSER_PORT:-4444}:80"
    environment:
      - TZ=${TIMEZONE:-Europe/Moscow}
      - FB_DATABASE=/database/filebrowser.db
      - FB_ROOT=/srv
      - FB_CONFIG=/config/settings.json
    volumes:
      - ./srv:/srv:rw
      - filebrowser_db:/database
      - ./settings.json:/config/settings.json:ro
    healthcheck:
      test: ["CMD-SHELL", "wget -q --spider http://127.0.0.1:80/health || exit 1"]
      interval: 15s
      timeout: 3s
      retries: 3
      start_period: 5s
    deploy:
      resources:
        limits:

          memory: 256M
    networks:
```

### 3.7 Взаимодействие phpPgAdmin + PostgreSQL и устранение ошибок (Пункт 8)

В методических указаниях содержится примечание: *«В случае проблем с подключением к СУБД из phppgadmin, задание пропустить»*. В процессе исследования выявлены две коренные причины этих проблем:
1. **Несовместимость шифрования паролей:** PostgreSQL 14+ использует по умолчанию `scram-sha-256`, тогда как устаревший модуль PHP в phpPgAdmin поддерживает исключительно алгоритм `md5`.
2. **Блокировка суперпользователя:** Директива `extra_login_security` в phpPgAdmin по умолчанию запрещает авторизацию под учетной записью `postgres`.

Обе проблемы решены в `06_phppgadmin_postgres/docker-compose.yml`:
* В контейнере PostgreSQL передана команда: `command: postgres -c password_encryption=md5` на образе `postgres:13.18-alpine`.
* В контейнере phpPgAdmin передана переменная: `PHP_PG_ADMIN_EXTRA_LOGIN_SECURITY=false`.

#### Листинг `06_phppgadmin_postgres/docker-compose.yml`:

```yaml
services:
  postgres-server:
    image: postgres:13.18-alpine
    container_name: vipkc_pg_postgres
    restart: unless-stopped
    command: postgres -c password_encryption=md5
    environment:
```

## 4. Верификация сетевой изоляции (Принцип Least Privilege)

Для подтверждения изоляции СУБД была проведена инспекция внутренней сети `vipkc_adminer_db_internal`:

```text
$ docker network inspect vipkc_adminer_db_internal --format '{{.Internal}}'
true
```

Значение `true` гарантирует, что Docker Daemon блокирует правила iptables на маршрутизацию пакетов за пределы хостового моста (`FORWARD` цепочка дропает любой внешний трафик). База данных физически недоступна из локальной сети колледжа или сети Интернет, но полностью доступна контейнеру веб-клиента.

## 5. Ответы на контрольные вопросы

### 5.1 Для чего используется Docker Compose?
**Ответ:**  
Docker Compose — это инструмент декларативной оркестрации многоконтейнерных приложений на одиночном узле (Docker Host). Он позволяет:
1. Описать всю инфраструктуру приложения (сервисы, сети, тома, переменные окружения, лимиты ресурсов, порядок запуска и проверки состояния) в виде одного или нескольких YAML-файлов.
2. Управлять жизненным циклом всего стека одной командой (`docker compose up -d`, `docker compose down`, `docker compose restart`).
3. Изолировать приложения друг от друга с помощью автоматического создания изолированных сетей bridge и пространства имен проекта (`COMPOSE_PROJECT_NAME`).

### 5.2 В каком формате обычно описывается Docker Compose проект?
**Ответ:**  
Проект описывается в текстовом формате **YAML** (`.yml` или `.yaml`), обычно в файле `docker-compose.yml` (или `compose.yaml` в современной Compose Specification). Корневыми разделами спецификации являются:
* `services:` — перечень запускаемых контейнеров, их параметров, переменных окружения, портов и зависимостей.
* `networks:` — описание пользовательских виртуальных сетей (драйверы bridge/overlay, подсети, шлюзы, флаг `internal`).
* `volumes:` — описание постоянных именованных томов для хранения данных вне жизненного цикла контейнеров.
* `configs:` и `secrets:` — управление конфигурационными файлами и конфиденциальными данными.

### 5.3 Как запустить несколько экземпляров проекта Docker Compose на одном сервере?
**Ответ:**  
Для запуска нескольких независимых экземпляров (инстансов) одного Compose-проекта на одном хосте необходимо обеспечить уникальность пространств имен и портов:
1. **Имя проекта (`Project Name`):** Передать уникальное имя через флаг `-p` или переменную `COMPOSE_PROJECT_NAME`:
   ```bash
   docker compose -p client_ivan up -d
   docker compose -p client_alex up -d
   ```
   Это создаст раздельные контейнеры, сети и тома с соответствующими префиксами (`client_ivan_web`, `client_alex_web`).
2. **Параметризация портов:** Опубликованные на хосте порты не могут пересекаться. Поэтому порты выносятся в переменные окружения (`ports: ["${HTTP_PORT}:80"]`), и каждый экземпляр запускается со своим `.env` файлом (например, порт `4444` для одного и `4445` для другого) через флаг `--env-file`.
3. **Раздельные каталоги или файлы:** Использование разных файлов переопределения (`-f docker-compose.prod.yml`).

### 5.4 Какие есть базовые команды для управления Compose проектом?
**Ответ:**  
* `docker compose up -d` — сборка (при необходимости), создание и запуск всех сервисов проекта в фоновом режиме (detached mode).
* `docker compose down` — корректная остановка и удаление контейнеров и сетей проекта (с флагом `-v` также удаляются постоянные тома).
* `docker compose ps` — отображение статуса контейнеров проекта (состояние healthcheck, порты, коды выхода).
* `docker compose logs -f [service]` — непрерывный просмотр журналов логирования (stdout/stderr) сервисов.
* `docker compose exec [service] [cmd]` — интерактивное выполнение команды внутри работающего контейнера (например, `docker compose exec database bash`).
* `docker compose restart [service]` — перезапуск одного или всех сервисов.
* `docker compose config` — валидация синтаксиса compose-файла и вывод результирующей конфигурации с подставленными переменными окружения.
* `docker compose build` — пересборка образов, для которых указана секция `build:`.

### 5.5 Какими способами контейнеры могут взаимодействовать в одном проекте?
**Ответ:**  
Контейнеры внутри одного Compose-проекта могут взаимодействовать следующими способами:
1. **Через пользовательские сети Docker (User-defined Bridge Networks) по DNS-имени сервиса (рекомендуемый способ):**  
   Docker предоставляет встроенный DNS-сервер (`127.0.0.11`). Контейнеры обращаются друг к другу по имени сервиса (например, `mysql-server:3306` или `database:5432`). Сети можно изолировать параметром `internal: true`.
2. **Через разделяемые тома (Shared Volumes):**  
   Несколько контейнеров могут монтировать один и тот же именованный том (`volumes`) или каталог хоста (bind mount) для обмена файлами (например, веб-сервер отдает статику, сгенерированную бэкенд-контейнером).
3. **Через разделяемый сетевой стек другого контейнера (`network_mode: "service:..."` или `container:...`):**  
   Контейнеры делят один сетевой интерфейс (`localhost`), что часто применяется в sidecar-паттернах.
4. **Через сокеты Unix (Domain Sockets):**  
   Передача IPC-сокетов через общий том (например, сокет PHP-FPM для Nginx или `/var/run/docker.sock`).
5. **Через разделяемую память (IPC, Shared Memory):**  
   С использованием директивы `ipc: "service:..."` или `shm_size` для высокопроизводительного обмена данными между процессами.
